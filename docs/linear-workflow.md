# Agent Office — Linear Workflow Standard

Linear is the **source of truth for work tracking** across the whole Office.
Every team (Lab / Spec / Dev) tracks its work in Linear; the human (via the
external Hermes agent) and Scrum Master read live status from there.

This is the Office-level manifest. The canonical Dev implementation lives in
`dev-crew/crew/FACTORY-STANDARD.md` and the `tech-pm` skills
(`linear-workflow`, `to-tickets`, `to-spec`, `task-dispatch`).

## Access

- Workspace / org: `Bonny factory`
- Team key: `BON`
- API: GraphQL at `https://api.linear.app/graphql`, header `Authorization: <LINEAR_API_KEY>`
- Token lives in `tokens/tokens.yaml` (gitignored); agents receive it via the
  `LINEAR_API_KEY` env var. One shared token — every agent can read/act on Linear.

## The Dev flow (spec → shipped)

1. **Spec arrives** — OpenSpec in the project repo (or a written spec for the effort).
2. **Adversarial review** — each involved agent reviews the spec from its own
   lens (product / engineering / infra / testability) and posts a verdict
   (`approve` / `needs-changes`) + at most 3 blocking findings.
3. **Plan & decompose** — tech-pm turns the reviewed spec into a plan and a
   Linear **Project**, then splits it into **tracer-bullet tickets**, each linked
   to that Project, with blocking edges between them.
4. **Implement + verify** — developer implements a slice on a
   `feature/<ticket>-slug` branch, brings it up on the team's dev-env and verifies
   it runs, then opens a PR and waits for review (no self-merge).
5. **Code review** — qa + manager review the PR against the spec.
6. **Merge** — only after review passes.
7. **Deploy to staging** — devops deploys merged code to the team's staging-env.
8. **QA verify** — qa verifies on staging, updates test plans, records a report;
   bugs are published on the bus (`bug.found`) and recorded durably.
9. **QA approve** — qa approves the build.

## Linear conventions

- **A product effort is a Linear Project**, not a synthetic parent "epic" ticket.
  Link every ticket to its Project; never invent a parent ticket just for grouping.
- **Tracer-bullet tickets**: vertical slices, each a complete demoable path
  (schema → API → UI → tests), sized to fit one context window. Declare blocking
  edges; work the frontier (blockers first).
- Every ticket has a clear title and a description with **acceptance criteria**.
- **AI-generated comments** are prefixed: `> *This was generated by AI.*`
- On finish an agent comments the result and moves the ticket state:
  - success + PR/reviewable artifact → **In Review**
  - success (no PR) → **Done**
  - failure / blocked → **Blocked**

## Deterministic completion

Task start/finish is signalled by the **runtime** (completion watcher), not only
by LLM comments. Dispatch messages include `Ticket <ID>` so the runtime can bind
events. On finish the factory best-effort:
- moves the Linear ticket state + auto-comments,
- pings the manager webhook,
- always publishes `task.started` / `task.finished` on the bus.

External API failures (Linear/manager) must not crash the agent — they are
best-effort; the Redis bus publish is the durable minimum.

## Team-specific usage

| Team | Linear usage |
|------|--------------|
| **Dev** (`dev-crew`) | Full flow above — Project + tickets → implement → PR → deploy → QA |
| **Spec** (`product-factory`) | Intake / spec tickets; artifacts are documents (specs), not code |
| **Lab** (`lab-crew`) | Research tickets; produces Research Packages, not code |

Lab and Spec teams track their (lighter) work as tickets too, so status is always
visible in Linear; they simply don't run the implement→deploy half of the flow.

## Rules / invariants

- **No spec → no work** (Dev). A task without a spec reference is rejected.
- Ticket state in Linear must reflect reality — no "documentation lie".
- Scrum Master (or the human) must be able to answer at any moment:
  "where is this project, and who is working on what" — purely from Linear + the bus.
- The escape hatch (critical override) is still recorded as tech-debt (GitHub
  issue or Linear ticket) — see `crew/OFFICE-STANDARD.md`.
